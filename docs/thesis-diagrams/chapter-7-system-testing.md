# 第7章 系统测试

## 7.1 测试的目的和方法

系统测试是系统开发完成后的重要验证环节，其主要目的是检验微博舆情分析系统的功能实现是否满足需求分析阶段提出的要求，系统性能是否达到预期指标，并验证系统在实际运行过程中的稳定性和可靠性。本章测试内容围绕数据采集、情感分析、数据展示、Spark 数据处理效率以及系统运行稳定性展开。其中，情感分析功能是系统的核心功能，因此本章对标准模式、快速模式和纯词典模式进行了重点测试和对比分析。

本章采用的测试方法包括功能测试、性能测试和准确率测试。功能测试主要采用黑盒测试方法，从用户操作角度验证系统页面、接口和业务流程是否能够正常运行；性能测试主要结合 Spark 作业执行结果和系统观察结果，分析数据处理优化前后的效率变化；准确率测试采用隔离测试集与人工标注标签进行对比，计算 Accuracy、Precision、Recall 和 F1 值等评价指标。所有情感分析相关数据均来自真实脚本运行输出，不使用人工编造的测试数字。

### 7.2.2 情感分析功能测试

情感分析功能是本系统的核心功能之一，其测试目标是验证不同情感分析模式在同一隔离测试集上的分类准确率、各类别识别能力和推理效率。测试时分别运行三种模式：标准模式、快速模式和纯词典模式。标准模式使用微调后的 ChineseBERT 模型直接推理；纯词典模式使用 `spark/sentiment_analyzer.py` 中 `SentimentLexicon.analyze_3class` 方法；快速模式采用三阶段级联策略，即先执行词典分析，若词典结果为高置信度则直接输出，否则调用 ChineseBERT 模型，当 BERT 置信度低于 0.55 且词典倾向为 neutral 时，回退采用词典中性判断。

测试脚本在 `backend-python` 目录下运行，模型加载路径为 `models/chinese-bert-wwm-ext`，BERT 推理时使用 `max_length=128`，并在 `torch.no_grad()` 环境下使用 GPU 加速。三种模式均在同一批 10000 条隔离测试集上评估，保证对比结果具有一致性。

表7-2 三种模式整体对比表

| 测试模式 | Accuracy | Macro F1 | 平均推理速度（ms/条） |
|---|---:|---:|---:|
| 标准模式（ChineseBERT） | 87.79% | 87.83% | 8.11 |
| 快速模式（三阶段级联） | 85.85% | 85.94% | 10.01 |
| 纯词典模式 | 64.21% | 63.30% | 0.06 |

从整体结果看，标准模式的 Accuracy 和 Macro F1 最高，说明微调后的 ChineseBERT 模型能够较好地捕捉微博文本中的上下文语义信息。快速模式的 Accuracy 为 85.85%，Macro F1 为 85.94%，低于标准模式但明显高于纯词典模式。纯词典模式推理速度最快，平均每条仅 0.06 ms，但由于规则和词典无法充分覆盖微博文本中的隐含语义、反讽表达和上下文依赖，其整体准确率明显低于深度学习模型。

测试结果：情感分析模块在 10000 条隔离测试集上完成三种模式真实评估，其中标准模式 Accuracy 为 87.79%，快速模式 Accuracy 为 85.85%，纯词典模式 Accuracy 为 64.21%，标准模式和快速模式均满足 85% 准确率要求。

## 7.3 性能测试

### 7.3.1 数据处理效率测试

数据处理效率测试用于评估系统 Spark 分布式数据处理流水线在数据清洗、分词处理、特征提取和情感分析各阶段的性能表现，以及 Spark 优化策略（Kryo 序列化、AQE 自适应查询执行、自适应分区合并、广播 Join）对各阶段的实际影响。测试使用 `weibo_senti_100k.csv` 数据集，分别选取 10,000 条、50,000 条和 99,999 条三种规模，在关闭优化和开启优化两种配置下各运行 2 次并取平均值。测试脚本为 `backend-python/scripts/spark_stage_perf_test.py`，每个阶段执行后强制触发 `count()` 动作以确保计时准确。优化前配置：AQE 关闭、分区合并关闭、使用 JavaSerializer、广播 Join 关闭；优化后配置：AQE 开启、分区合并开启、使用 KryoSerializer、广播 Join 阈值 10 MB。

从分阶段结果看，特征提取阶段对 Spark 优化最为敏感，50,000 条规模下提升达到 16.53%，99,999 条下提升 7.92%。特征提取涉及 explode、groupBy、词频统计和 UDF 关键词匹配等 Spark SQL 操作，AQE 能够在运行时动态调整 Shuffle 分区数，Kryo 序列化能够降低中间数据传输开销，因此该阶段受益最大。数据清洗阶段在较小规模下有 6%–9% 的提升，但在 99,999 条规模下提升不明显，原因是清洗阶段以 Python UDF 为主，Spark SQL 层面的优化对 Python 进程内的正则匹配和字符转换影响有限。分词处理阶段使用 jieba 中文分词库，属于 CPU 密集型的逐词计算操作，Spark 优化对其影响有限，在 99,999 条规模下甚至出现 5.54% 的性能下降，原因是 AQE 动态调整分区可能引入额外的 Shuffle 开销。情感分析阶段使用词典规则 UDF 逐条处理，同样属于 CPU 密集型计算，Spark 优化措施无法深入 Python 进程内部逻辑，因此提升幅度最小，个别规模下甚至略有波动。

从总耗时看，50,000 条规模下优化效果最明显，达到 9.74%；10,000 条下为 5.80%；99,999 条下为 3.34%。99,999 条规模下优化幅度下降的原因在于大数据量场景下每个分区的数据体积增大（单任务达 10 MB），Python UDF 序列化瓶颈更为突出，AQE 和 Kryo 对 JVM 内部执行路径的优化难以弥补 Python 进程间数据传输开销的增长。

#### UDF 实现方式优化对比

为进一步验证 Python UDF 序列化开销对性能的影响，本文对数据清洗阶段的 UDF 实现方式进行了对比测试。测试对比了四种方案：普通 Python UDF（逐行序列化）、mapPartitions 批量处理（按分区批量处理，减少序列化次数）、Spark SQL 原生 regexp_replace 链式调用（纯正则部分，完全在 JVM 内执行）、以及 SQL 正则 + mapPartitions 混合方案（正则在 JVM 执行，表情映射和繁简转换在 Python 侧按分区处理）。测试数据量为 10,000 条，每种方案运行 2 次取平均。测试脚本为 `backend-python/scripts/udf_benchmark_v2.py`。

表7-10 数据清洗阶段UDF实现方式对比

| 方案 | 清洗耗时（秒） | vs 普通UDF提升 |
|---|---:|---:|
| 普通 Python UDF | 7.60 | — |
| mapPartitions 批量处理 | 5.01 | +34.09% |
| Spark SQL 纯正则 | 2.59 | +65.94% |
| SQL + mapPartitions 混合 | 5.04 | +33.65% |

表7-11 全流程UDF方案对比（清洗+分词+情感分析）

| 阶段 | 普通UDF耗时（秒） | mapPartitions耗时（秒） | 提升幅度 |
|---|---:|---:|---:|
| 数据清洗 | 7.60 | 5.01 | +34.09% |
| 分词 | 6.57 | 7.24 | -10.26% |
| 情感分析 | 6.78 | 5.72 | +15.63% |
| 总耗时 | 20.95 | 17.97 | +14.21% |

从数据清洗阶段对比看，Spark SQL 原生 regexp_replace 方案耗时仅 2.59 秒，比普通 Python UDF 快 65.94%，这是因为正则替换操作完全在 JVM 内部执行，无需 Python 进程间序列化和反序列化。mapPartitions 方案和 SQL + mapPartitions 混合方案耗时均约 5 秒，比普通 UDF 快约 34%，减少了逐行序列化次数。需要指出的是，Spark SQL 纯正则方案仅覆盖了去除 HTML 标签、URL、@提及、#话题#和多余空白等正则操作，未包含表情符号映射、繁简转换和全角半角转换，因此输出行数与完整清洗方案略有差异（9972 vs 9970）。

从全流程对比看，mapPartitions 方案总耗时 17.97 秒，比普通 UDF 快 14.21%。其中数据清洗和情感分析阶段分别快 34.09% 和 15.63%，说明按分区批量处理能够有效减少 JVM–Python 之间的数据传输开销。分词阶段 mapPartitions 反而慢 10.26%，原因是分词阶段需要在 mapPartitions 内部进行 Row 对象的字典转换和重构，而 jieba 分词本身是逐词计算的 CPU 密集操作，序列化开销占比不高，额外的对象转换开销反而抵消了批量传输的优势。

注：由于当前测试环境 Spark 3.5.3 内置 Arrow Java 12.0.1 与 Java 21 的 sun.misc.Unsafe 反射机制不兼容，Pandas UDF（向量化 UDF）无法正常执行，因此本次未纳入 Pandas UDF 的测试结果。在 Arrow Java 14+ 或 Java 17 以下版本的环境中，Pandas UDF 使用 Apache Arrow 进行 JVM–Python 批量数据传输，预期性能将优于 mapPartitions 方案。

测试结果：Spark 分阶段性能测试在 10,000 条、50,000 条和 99,999 条三种规模下完成，优化后总耗时分别降低 5.80%、9.74% 和 3.34%，特征提取阶段受益最大。UDF 实现方式对比表明，将数据清洗中的正则操作替换为 Spark SQL 原生函数可提升 65.94%，采用 mapPartitions 批量处理全流程可提升 14.21%。

## 7.4 本章小结

本章围绕微博舆情分析系统开展了系统测试，测试内容包括测试目的和方法、功能测试、情感分析准确率测试、数据展示测试、数据处理效率测试和系统稳定性测试。为保证论文数据真实性，本章所有已填写的数值均来自真实脚本输出；对于当前环境未执行的测试项，均明确标注为待补充，未使用未经验证的数字。

情感分析测试是本章重点。测试结果表明，在 10000 条隔离测试集上，纯词典模式 Accuracy 为 64.21%，Macro F1 为 63.30%；快速模式 Accuracy 为 85.85%，Macro F1 为 85.94%；标准 ChineseBERT 模式 Accuracy 为 87.79%，Macro F1 为 87.83%。三种模式呈现出从词典到级联再到 BERT 的准确率梯度，验证了系统采用词典规则与深度语义模型相结合的技术路线具有有效性。其中，标准模式和快速模式均达到 85% 以上准确率要求，说明系统核心情感分析功能能够满足设计目标。

性能测试方面，Spark 分阶段性能测试在 10,000 条、50,000 条和 99,999 条三种规模下完成，开启 Kryo 序列化、AQE 自适应查询执行、自适应分区合并和广播 Join 后，总耗时分别降低 5.80%、9.74% 和 3.34%，其中特征提取阶段受益最大（50,000 条规模下提升 16.53%）。UDF 实现方式对比测试进一步表明，将数据清洗中的正则操作替换为 Spark SQL 原生 regexp_replace 可提升 65.94%，采用 mapPartitions 按分区批量处理全流程可提升 14.21%，验证了减少 Python UDF 序列化开销对提升 Spark 作业效率的有效性。稳定性方面，当前环境已经验证情感分析核心推理链路能够连续完成 10000 条测试集评估，但严格 24 小时连续运行测试仍需在完整部署环境中补充。

综上，系统在核心功能和情感分析准确率方面达到了预期目标，Spark 优化效果在多种规模和多种实现方式下均得到验证，系统整体功能具备可用性。后续工作可进一步补充部署环境下的数据采集、前端展示和 24 小时稳定性测试结果，使系统测试内容更加完整。
